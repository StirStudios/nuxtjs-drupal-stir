# Stir Webform capability

This optional layer owns the Webform submission endpoint, submission
limits, Webform rendering components, and Cloudflare Turnstile integration.

The full compatibility preset includes it. The minimal preset does not expose
the Webform submission route or load the Turnstile Nuxt module.

Capability-focused downstream applications may consume it directly:

```ts
export default defineNuxtConfig({
  extends: ['@stir/base/layers/webform/nuxt.config'],
})
```

The layer composes the shared website platform plus mandatory Turnstile
protection; it does not load auth, SEO, editorial, analytics, scripts, or
integrations. A later form/field boundary will allow Webform-only consumers to
use the foundation without the complete website renderer.

The shared widget default is `appearance: 'interaction-only'`: validation stays
enabled, while Cloudflare requests visible interaction only when needed.
Downstream projects may override the appearance through `stirTheme.turnstile`.

## Payload boundary

`WebformForm` normalizes and validates the Drupal payload once through
`normalizeWebformDefinition`. Field components consume only that canonical
shape; they do not repeat boolean, cardinality, property-name, or field-type
coercion.

Custom Elements camel-cases every nested key on the way from Drupal, never a
value. So identity always comes from a value: a field's or composite part's
`#name`, an option map's `#optionKeys` (likert: `#questionKeys`,
`#answerKeys`), and a condition rule's `name`. Never take a Drupal name from
an object key.

Submission field names, composite keys, and selected option values are sent
back to Drupal exactly as provided. Never apply generic snake-case or
camel-case conversion to submission data. The only scalar wire conversion is
boolean values to Drupal's `1` and `0` representation. Each value has the
shape Webform stores: a list for a multiple field and for checkboxes, an
object for a composite (a list of them when it takes several values), and an
object keyed by question for a likert. `createWebformState` builds that shape.

### Conditions

`#conditions` is Webform's `#states` with element names as values.
`resolveWebformFieldStates` evaluates them as Drupal's
`WebformSubmissionConditionsValidator` does (aliases such as `invisible` and
`optional`, triggers such as `checked`, `filled`, `!value`, `pattern`,
`between`, and `and`/`or`/`xor`), so a field is shown, hidden, required and
disabled by the rules that will judge the submission. A condition naming a
field the form does not have is ignored, as Drupal ignores it, with a console
warning.

### Element types

Aliases resolve at the boundary to the component and value shape they share
with a family (for example `webform_checkboxes_other` to `checkboxes`,
`webform_time` to `time`, `webform_rating` to radios of its scale). Every
composite renders its parts through `FieldComposite`. A Webform composite's
own `#required` only marks it, as in Webform; each part's `#required` is what
is enforced.

An element type the layer has no component for is never shown as an empty
field: it is reported with `console.error`, left out of the form, its state
and its validation, and left to Drupal to judge. Add a component and its type
to `WEBFORM_FIELD_TYPES` when a project needs one.

### Contract

The versioned producer schema and fixtures are mirrored under
`contracts/stir-tools/v1`. The kitchen-sink fixtures are generated by Stir
Tools from a real Webform, and `tests/contracts/webformKitchenSink.spec.ts`
replays them: every element must render, Drupal's accepted sample must pass
validation, and the layer must submit exactly that sample.

Compatibility adapters for producers before contract 1.32 (`#conditions`
built from camel-cased `#states`, address parts without `#type`) live only in
the boundary and should not be used by presentation components. Remove them
once every site runs Stir Tools with contract 1.32.
